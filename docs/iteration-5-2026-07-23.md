## 本轮目标

先修复“网页划词翻译仍返回英文、组件内测试却能返回中文”的路径不一致，再把设置组件改成由后台状态驱动的来源优先控制面。用户应先明确选择“本地 Ollama”或“项目服务器”，随后只看到该来源真实存在的模型；用户不需要理解 SSH 隧道、模型引用前缀或 Ollama 常驻细节。

本轮遵循以下顺序：

1. 先记录问题、目标状态和验收条件；
2. 为一个问题建立一个能够失败的最小复现；
3. 只修改该问题所需的代码并运行针对性测试；
4. 通过后再进入下一项；
5. 最后统一更新 README、中文说明、Greasy Fork 文案和发布元数据。

## 已确认的问题

### P0：网页翻译与组件测试结果不一致

- 已从真实 Tampermonkey 组件确认，网页请求使用的确实是 `remote:project-server:qwen3:30b` 和 `Simplified Chinese`，因此本次故障不是目标语言或模型选择错误。
- 网页划词会附带页面上下文，组件测试使用空上下文。页面上下文中的 `🎙️` 被 `ensure_ascii=False` 写入 Windows GBK 控制台时触发 `UnicodeEncodeError`，请求在到达 Ollama 前就返回 502。
- 即使请求成功，模型对 `Categorical-SAC` 等短技术词也可能原样返回英文；旧后台没有检查中文目标是否得到中文结果，因此会把纯英文当作成功。
- 已把请求日志降级为不可影响业务的诊断路径，并在中文目标返回纯英文时执行一次更严格的同模型重试；重试后仍不含中文则返回上游失败，不再把英文伪装成成功翻译。
- 后续设置重构仍需让组件测试与网页划词共用一个经验证的请求快照构造器，防止未来重新产生设置路径差异。

### P1：模型列表包含不存在或不适合翻译的静态选项

- `TRANSLATION_MODELS` 在用户脚本中写死了多个本地模型。
- `mergeTranslationModelOptions()` 先加入静态模型，再加入后台发现结果和“自定义模型”，所以即使本机 Ollama 不可达，界面仍显示一组看似可选的本地模型。
- 后台当前会把 `/api/tags` 中的 embedding/reranking 模型也当作翻译模型返回。
- 修复后，正常界面只显示后台当前发现且可用于文本生成的模型；不再用静态模型或自由文本输入伪造可用项。

### P1：组件与后台连接状态脱节

- **Use project server**、**Initialize local model**、**Start local service**、**Keep loaded** 和 **Unload** 目前会同时创建，而不是根据真实状态出现。
- 当托盘已经连接项目服务器时，网页仍要求“Use project server”；当本机 Ollama 不可达时，仍显示本地初始化和常驻操作。
- `/translate/health` 只以“当前选择的来源”为主状态，同时附带所有来源的模型列表。当前选择本地模型且本地离线时，响应会同时出现 `ollama_reachable: false` 和可用远程模型，前端因此显示自相矛盾的信息。
- 修复后，后台显式返回各来源的可达性和模型状态；前端不再从一个总状态猜测多个来源。

### P1：纠偏——离线来源被过度隐藏

- 第一版紧凑组件把“只显示真实模型”错误扩展成“只显示可达来源”。本地 Ollama 关闭而项目服务器在线时，界面只剩服务器模型，本地来源和启动入口一起消失。
- 正确顺序是先选翻译来源，再选该来源的模型：本地离线时显示 **Start local Ollama**，服务器未连接时显示 **Connect server**；动作成功并刷新健康状态后，才显示该来源真实发现且可用于文本生成的模型。
- 服务器已经连接时只显示 **Connected** 和服务器模型，不再显示重复的连接提示。两边都在线时保留两个来源入口，但模型选择器只列出当前来源的模型。
- 网页仍不保存 SSH 地址、密码或密钥。**Connect server** 只打开托盘负责的 Remote Service 窗口；**Start local Ollama** 只触发固定的本地托盘动作。

### P2：普通设置暴露了过多实现细节

- “自定义模型”自由文本框、目标语言自由文本框以及五个模型/服务操作会让普通翻译变成系统管理任务。
- 常用路径应只保留真实模型选择和翻译测试；目标语言与模型常驻管理放进折叠的高级设置。
- 项目服务器的 SSH/API 配置仍由托盘负责，网页只显示“已连接”的事实，不提供登录或连接表单。

### P2：卸载接口可能无法真正卸载已常驻模型

- 当前卸载流程在移除 pin 之前调用生成接口，pin 逻辑可能重新覆盖 `keep_alive: 0`。
- HTTP 返回不能单独作为释放显存的证据；针对远程模型仍要以对应来源的运行模型列表为准。
- 修复后，先移除 pin，再发送卸载请求，并等待运行列表确认；超时必须返回真实的“仍在运行”状态。

### 4. 重构设置组件（已完成）

组件服务于“正在阅读论文、希望快速选择真实模型并翻译”的用户，单一任务是确认当前翻译能力，而不是管理基础设施。

视觉令牌：

- `ink` `#10121B`：组件背景；
- `surface` `#191C2A`：控件与分区；
- `text` `#EEF1FA`：主要文字；
- `muted` `#9AA3B8`：说明文字；
- `connected` `#55C98F`：真实可用状态；
- `accent` `#8292FF`：当前模型与主要操作。

字体角色：标题使用 `Segoe UI Variable Display`，正文使用 `Segoe UI Variable Text, Microsoft YaHei UI`，模型标识使用 `Cascadia Mono`。不加载网络字体。

桌面与窄屏布局：

```text
┌─────────────────────────────────────┐
│ Local Read & Translate       ● Ready│
├─────────────────────────────────────┤
│ Translation                         │
│ Project Server · connected          │
│ [ qwen3:30b                      ▾ ] │
│ [ Test translation ]                │
│ ▸ Advanced                          │
├─────────────────────────────────────┤
│ Read aloud                 ▸         │
└─────────────────────────────────────┘

无服务时：
┌─────────────────────────────────────┐
│ Local Read & Translate      Offline │
│ Local service is not running.       │
│ [ Start local service ]             │
└─────────────────────────────────────┘
```

标志性元素是“来源状态轨”：状态、来源和模型沿同一条紧凑信息线呈现，让用户一眼看到请求会去哪里。其余视觉保持克制，不添加装饰性渐变或无意义动画。

原自我审查结论“来源已经由模型数据表达”经真实使用证明不成立：模型数据只能表达已连接来源，无法提供启动本地 Ollama 或连接服务器的入口。第 6 项用两行来源状态轨纠正这一点，但仍不引入双栏基础设施仪表盘或重复的凭据表单。

验收：

- 离线时只显示启动本地服务；
- mediator 在线时始终显示本地与项目服务器两个来源入口；
- 只有实际可执行的上下文操作才出现；
- 键盘焦点可见，窄屏不横向溢出，`prefers-reduced-motion` 下不执行非必要动画；
- 不使用 `innerHTML`、`insertAdjacentHTML` 或其他 Trusted Types 不兼容的 HTML 字符串注入。

验收结果（2026-07-23）：

- 设置组件改为单列紧凑结构：顶部就绪状态、来源状态轨、一个真实模型选择器和一个测试操作；目标语言与模型生命周期收进 **Advanced**，TTS 收进 **Read aloud**；
- 组件通过 `deriveTranslationSettingsView()` 从 mediator 与逐来源健康数据生成视图，不再维护第二套“已连接/未连接”状态；
- 在线且项目服务器可达时直接显示 `Project Server · connected` 和后端发现的模型，不创建 **Use project server** 或 **Initialize local model**；
- mediator 离线时只显示 **Start local service**，并隐藏模型、翻译测试、Advanced 与 Read aloud；在线但没有真实模型时显示空状态，不伪造默认选项；
- 来源已连接但只有 embedding/reranking 等不合格模型时，状态轨继续显示该来源已连接，只提示安装生成模型；健康请求失败时进入明确的 **Unavailable**，不会停留在自相矛盾的 **Checking**；
- 目标语言由自由文本框改为受支持语言选择器，旧设置中的空值或非法值迁移为 `Simplified Chinese`；
- 键盘焦点、窄屏布局和 `prefers-reduced-motion` 均有明确样式；Trusted Types 源码回归继续禁止 HTML 字符串注入；
- 启动成功、离线和网络错误提示已移除旧的“初始化本地模型”与 `run start.bat` 文案，统一指向设置面板或托盘；
- 用户脚本核心测试增至 **41 passed**，覆盖离线、远程可达、已连接但无生成模型、健康失败、stale pin、目标语言迁移和旧操作移除。

以上第 4 项验收结果记录第一版紧凑组件，不再代表待发布的最终交互；第 6 项通过后将更新对应结果、版本与总测试数。

- 已 pin 但未运行的模型显示 **Remove keep-alive**；卸载端点先查 `/api/ps`，模型已退出时只清 pin，不发送会触发加载的生成请求；

### 7. 修复后台刷新反复进入 Checking（已完成）

问题复现：

- 点击 **Test translation** 后，翻译请求本身已经成功，但成功分支会立即调用 `checkTranslationStatus()`；
- 旧健康检查在发送请求前无条件把 `translationHealthPayload` 置空，因此组件把完整的 Ready 视图替换成 **Checking translation sources...**，直到健康响应返回；
- 同一个破坏性刷新还存在于来源/模型切换、常驻、卸载、本地服务启动完成和来源启动轮询；
- 来源轮询旧实现每秒发起一次最长 5 秒的健康请求，慢响应时会并行堆积；先发后到的旧响应也可能覆盖用户已经切换到的新来源或模型；
- 翻译测试成功后再切换来源、模型或目标语言时，旧结果仍然显示；常驻/卸载尚未返回时切换模型，旧生命周期响应也可能覆盖新模型的按钮状态。

修复与验收（2026-07-23）：

- `checkTranslationStatus({ preserveVisibleState: true })` 在后台刷新期间保留最后一个有效来源视图；首次打开且没有缓存时才显示 **Checking**，真实失败仍进入 **Unavailable**；
- 健康请求使用递增请求编号，所有成功、错误和超时回调都会忽略已经过期的响应；
- 来源动作轮询改为等待本轮健康请求完成后再安排下一轮，并使用绝对 120 秒截止时间，不再叠加慢请求；
- 来源、模型或目标语言变化会取消仍在运行的旧翻译测试并清除旧结果；模型切换立即用现有健康数据重绘生命周期操作；
- 常驻/卸载请求也使用独立操作编号，切换来源或模型后，旧响应不能再改写新选择的按钮与错误提示；
- 延迟健康响应的普通网页隔离复验确认：来源切换、成功测试翻译和模型切换期间均不出现 **Checking translation sources...**，模型切换后显示 **No translation test yet.**；
- userscript 核心测试为 **48/48 passed**，完整 Python 测试为 **212 passed, 17 subtests passed**，JavaScript 语法、Python 编译和 `git diff --check` 通过；
- 隔离页只使用模拟 `/health`、`/translate/health` 与 `/translate` 响应，没有连接真实翻译来源、启动本地 Ollama或加载远程模型。

## 明确不做的事情

- 网页脚本不直接保存或提交 SSH 凭据；
- 不把远程地址、密码、密钥路径暴露给网页；
- 不在翻译失败时未经用户同意切换到另一个来源；
- 不把不存在的默认模型显示为可用模型；
- 不在本轮顺便改变公式复制、公式朗读或 TTS 音色契约。
